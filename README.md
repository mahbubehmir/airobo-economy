# رصدخانه قیمت میلگرد — داشبورد داده و تحلیل دستی

این نسخه برای یک محصول هدف تنظیم شده است: **میلگرد آجدار سایز ۱۴، استاندارد A3، ذوب‌آهن اصفهان**. خروجی پروژه دو مسیر جدا دارد:

1. **گزارش فنی و آماری:** قیمت، روند، درصد تغییر روزانه/هفتگی، نوسان ۲σ، مقایسه عددی دو منبع و سوابق جمع‌آوری.
2. **محتوای اقتصادی/رسانه‌ای با نگارش انسانی:** دفتر تحلیل اقتصادی و سه پست آماده انتشار در Streamlit ذخیره می‌شوند. برنامه به‌جای شما علت اقتصادی یا متن رسانه‌ای تولید نمی‌کند.

## منابع داده

- **آهن‌تایم:** قیمت جاری از ردیف کارخانه ذوب‌آهن اصفهان استخراج می‌شود؛ کد قیمت کیلویی را از ستون مخصوص کارخانه می‌گیرد و مقدار نامعتبر را رد می‌کند. جدول تاریخ/قیمت نمودار نیز به‌عنوان تاریخچه ذخیره می‌شود.
- **فولادسل:** تاریخ و قیمت ردیف‌های موجود در جدول تاریخچه صفحه اختصاصی میلگرد ۱۴ اصفهان استخراج می‌شوند. صفحه بررسی‌شده در عنوان عمومی خود همه جزئیات استاندارد و کارخانه را به‌صورت صریح نشان نمی‌دهد؛ قبل از تفسیر اقتصادی واگرایی، مشخصات SKU و شرایط اعلام قیمت را دستی با صفحه کامل تطبیق دهید.

**محدودیت شفاف:** داده‌های فولادسل در اجرای مورد بررسی ۷ تاریخ پراکنده داشتند؛ این به معنی آرشیو روزانه کامل یا پوشش چندماهه تضمین‌شده نیست. اگر صفحه یا ساختار HTML تغییر کند، collector باید خطا بدهد و نباید قیمت کالای مشابه را جایگزین کند. داده خام وبگاه‌ها به زمان و شرایط همان منبع وابسته است.

## راه‌اندازی محلی در ویندوز

در پوشه پروژه (`D:\airobo-economy`) و با همان محیط پایتون، ابتدا وابستگی‌ها را نصب کنید:

```cmd
python -m pip install -r requirements.txt
```

اجرای جمع‌آوری و به‌روزرسانی گزارش‌های فنی (اجرای اول فوری، سپس هر ۲۴ ساعت):

```cmd
python main.py
```

داشبورد Streamlit را در **پنجره CMD جداگانه** اجرا کنید:

```cmd
python -m streamlit run app.py
```

سپس آدرس محلی‌ای که Streamlit در ترمینال نشان می‌دهد ــ معمولاً `http://localhost:8501` ــ در مرورگر باز کنید. برای گزارش فنی و داشبورد می‌توان از همان دیتابیس موجود `data/rebar_observatory.sqlite3` استفاده کرد. **دیتابیس را پاک نکنید.** داشبورد جدول‌های جداگانه `economic_journal` و `media_posts` را به‌صورت خودکار به همان SQLite اضافه می‌کند؛ جدول قیمت و تاریخچه موجود دست‌نخورده می‌ماند.

## اجرا با Docker Compose

نیازمند Docker Desktop و `docker compose` است. در پوشه دارای `docker-compose.yml` اجرا کنید:

```cmd
docker compose up --build -d
```

این دو سرویس را بالا می‌آورد:

- `rebar-watch`: جمع‌آوری منابع و بازسازی گزارش فنی، اولین اجرا فوری و سپس طبق زمان‌بندی.
- `dashboard`: داشبورد Streamlit روی `http://localhost:8501`.

مشاهده لاگ:

```cmd
docker compose logs -f rebar-watch
docker compose logs -f dashboard
```

توقف سرویس‌ها:

```cmd
docker compose down
```

دیتابیس در `./data` و گزارش‌ها در `./output` با volume حفظ می‌شوند. برای اجرای Docker روی دیتابیس فعلی ویندوز، فایل SQLite باید در پوشه `data` پروژه‌ای باشد که Compose از آن اجرا می‌شود؛ کپی دیتابیس حین اجرا توصیه نمی‌شود.

## بخش‌های داشبورد

- **نمای کلی:** آخرین قیمت‌ها، تاریخ‌های موجود، روند قیمت و میزان تکمیل اقلام تحویلی.
- **روند و درصد تغییر:** نمودار قیمت هر منبع، تغییر نسبت به مشاهده قبلی، درصد تغییر هفتگی و جدول شامل تاریخ مرجع محاسبه.
- **نوسان غیرعادی (۲σ):** بازده جاری با میانگین ± دو انحراف معیار نمونه‌ایِ حداکثر ۲۰ بازده قبلی مقایسه می‌شود؛ حداقل پنج بازده قبلی لازم است. بازده جاری وارد مبنا نمی‌شود. این پرچم علت اقتصادی را اثبات نمی‌کند.
- **واگرایی منابع:** تفاوت قیمت در تاریخ‌های مشترک؛ ردیف آخرین داده‌ها با تاریخ متفاوت جداگانه علامت‌گذاری می‌شود و نباید مقایسه هم‌زمان تلقی شود.
- **دفتر تحلیل اقتصادی دستی:** فرم برای «چه شد؟»، «چرا ممکن است رخ داده باشد؟»، شواهد موافق/مخالف، پیامد برای سازنده/مصرف‌کننده/سرمایه‌گذار خرد، خط تصمیم، میزان اطمینان و منابع. پنج ورود حداقل پیشنهادی تسک را می‌توانید ثبت، ویرایش و خروجی Markdown بگیرید.
- **پست‌های رسانه‌ای:** ثبت/ویرایش پست؛ کنترل تیتر حداکثر ۷ کلمه، حداکثر ۱۲ خط و الزام خط پایانی تصمیم. برای «داده در برابر شایعه» منبع الزامی است. سه پست و یک مورد شایعه‌سنجی در شاخص پیشرفت نمایش داده می‌شوند.
- **وضعیت داده و اجراها:** مشاهده رکوردها، تاریخ مبنا، متن خام، لینک منبع و سوابق آخرین اجراها.

ذخیره یک تحلیل یا پست، فایل‌های زیر را در `output` به‌روز می‌کند:

- `economic_journal.md`
- `media_posts.md`

این دو فایل از متون ثبت‌شده توسط شما ساخته می‌شوند؛ مدل زبانی آن‌ها را نمی‌نویسد.

## مبنای محاسبات

- **درصد تغییر نسبت به مشاهده قبلی:** `(قیمت فعلی / قیمت مشاهده قبلی − ۱) × ۱۰۰`. اگر بین مشاهدات چند روز فاصله باشد، این شاخص بازده فاصله مشاهده‌هاست، نه الزاماً بازده یک روز تقویمی.
- **درصد تغییر هفتگی:** قیمت جدید با آخرین مشاهده در یا قبل از تاریخ ۷ روز قبل مقایسه می‌شود. اگر مشاهده مرجع موجود نباشد، مقدار خالی نمایش داده می‌شود.
- **نوسان ۲σ:** شرط `|r_t − میانگین بازده‌های قبلی| > 2 × انحراف معیار نمونه‌ای بازده‌های قبلی`؛ تا ۲۰ بازده قبلی و حداقل ۵ بازده.
- **واگرایی:** `abs(P1 − P2) / ((P1 + P2) / 2) × 100`. قیمت‌های دارای تاریخ یکسان با ردیف جدا از آخرین قیمت‌های تاریخ متفاوت گزارش می‌شوند.

## فرایند توسعه و ثبت تغییرات

در مخزن فعلی، شاخه اصلی پروژه `main` است و تغییرات با استفاده از Git ثبت و در GitHub نگهداری می‌شوند.

برای حفظ کیفیت کد، بهتر است هر تغییر مستقل پس از بررسی و اجرای آزمون‌های مرتبط، با یک پیام روشن و متناسب با ماهیت تغییر ثبت شود.

در توسعه تیمی، می‌توان از ساختار شاخه‌ای زیر استفاده کرد:

- `main`: نسخه اصلی و پایدار پروژه
- `develop`: شاخه یکپارچه‌سازی تغییرات
- `feature/collectors`: توسعه و اصلاح جمع‌آوری داده‌ها
- `feature/analysis`: توسعه محاسبات و تحلیل داده‌ها
- `feature/streamlit-dashboard`: توسعه داشبورد

این ساختار پیشنهادی است و به معنی ایجاد شدن تمام این شاخه‌ها در مخزن فعلی نیست.

پیش از ارسال تغییرات به GitHub، لازم است وضعیت مخزن بررسی شود و آزمون‌های مرتبط با تغییرات اجرا شوند. پیام هر کامیت نیز باید به‌روشنی نشان دهد چه تغییری در پروژه انجام شده است.
